Option (a) is **not** scheduled; instead the deferred fix is mutual TLS on the outbound port with the peer id derived from the client certificate (zero wire change, a PKI/deployment decision that reverses the server-role `verify_none` choice). Trust assumption, limits of (b) and the deferred design are recorded in `notes/plans/issues/broker-outbound-peer-identity-deferral.md`.
2. **M-4 association messages.** Require an authorized principal (breaks an unauthenticated proxy deployment) versus only restricting `sourcePeerId` to the connection's own id plus a size cap. Default: both; every in-tree proxy configuration authenticates.
3. **N-2 defaults.** Receive/handshake/shutdown timeout default (proposed 60 s) and connection cap default (proposed 4096) as `TcpServerBase` constructor parameters, with today's unbounded behaviour reachable by passing 0. Default: yes.
4. **S-2 scope.** Escaping template variables changes the bytes sent for tokens containing reserved characters. Default: escape, behind a config flag `escapeTemplateVariables` defaulting to true, with a release note.
5. **O-3 double-fork.** Changes the detached child's parent pid. Default: do it; nothing in-tree reads the child's ppid.
   **Decided 2026-09-05: no double fork.** It would make the detached handle non-waitable (`waitpid` fails with `ECHILD`; the existing test at `TestBaselibDefault.h:1623` waits on a detached child), break parity with Windows (a detached process handle stays waitable there) and expose `terminateProcess` to pid reuse once init reaps the grandchild. Instead: an opportunistic reaper (abandoned detached pids are polled with `waitpid( WNOHANG )` from `createProcess` and from every handle release), `/dev/null` on the non-redirected standard descriptors, `Detach|Redirect` implemented on Linux (the pipes are valid for the callback's lifetime, as on Windows) and no wait on releasing a detached handle. See O-3 below.
6. **A-12.** Fix the lock-graph cycle (default) versus a TSan suppression plus a record. The cycle is not a reachable deadlock, so this is a code-hygiene decision.
7. **R-4 contract.** Detect and tolerate unsubscribe-from-callback (default) versus documenting it as forbidden and asserting (`BL_RT_ASSERT`) on re-entry.
8. **R-5 shape.** Outbound message queue (default) versus a narrower guard that rejects an inbound message while a send is pending (turns the silent overwrite into a loud `TargetPeerQueueFull`-style error; cheaper, but drops the ack the peer is waiting for).

## A-12 The recorded `AsyncExecutor` task-lock TSan inversion: real lock-graph cycle, not a reachable deadlock — Info/decision — complexity Medium

- **Where.** Edge 1: `async/AsyncExecutorImpl.h:397` (`onOperationTaskReady` holds `base_type::m_lock`) → `:452` `scheduleAsyncCall` → `:374` `postCompletionCallback` → `:1061-1085` `m_completionTasksQueue->push_back` → `tasks/ExecutionQueueImpl.h:798` (queue lock) → `:694` `scheduleNothrow` → `tasks/TaskBase.h:1115` (the completion `SimpleTask`'s lock). Edge 2: `TaskBase.h:1372` (`SimpleTaskWithContinuation::onExecute` holds the SimpleTask lock while invoking the callback) → `AsyncExecutorImpl.h:195` (`m_executeLock`) → `:206` (`ExecutorTask::m_lock`).
- **Decided 2026-09-06: suppression plus a record, no code change (decision 5).** The review's restructure would not remove the edge: `scheduleAsyncCall` is also reached from `scheduleCall` (called under the task lock from `TaskBase::scheduleNothrow`) and from `requestCancel`, so the task-lock → queue-lock edge survives. Implemented instead: new `projects/make/toolchain/tsan-suppressions.txt` with the single entry `deadlock:bl::detail::AsyncExecutorImplT*::ExecutorTaskT*::scheduleAsyncCall`, wired in by appending `suppressions=$(abspath …)` to the `TSAN_OPTIONS` export in `projects/make/toolchain/clang-analysis.mk`, and the record `notes/plans/issues/async-executor-tsan-inversion-record.md`. Proof that the suppression does what it claims: `utf_baselib_async --run_test=AsyncCB_BasicTests` under TSan reports **50** lock-order-inversion warnings without it and **0** with it; `utf_baselib_tasks` goes from 217 to 78. The 78 that remain are a different, pre-existing class (`ExternalCompletionTaskIfT::onExecute` → `ExecutionQueue::push_back`), deliberately left reported and recorded in the same record.

- **Why it cannot close.** Thread 1 acquires the lock of the task at the front of the pending queue, which `postCompletionCallback` just moved there from Ready; a task in Ready has already released its `onExecute` lock. Thread 2 holds a SimpleTask lock only while that task is Executing. The same `TaskInfo` cannot be Ready and Executing at once, so the two edges are never held simultaneously for one mutex instance; TSan reports the cycle across historical acquisitions of the reused completion task (`OptionKeepAll`, `:876-881`). This is the 255-report class recorded in `pr-review-fable51-residual-findings-status.md` as "a separate decision".
- **Design intent.** `:177-193` documents `m_executeLock` first, then the task lock; nothing documents the task-lock → queue-lock edge, which exists only because the accounting and the post share one critical section.
- **Options.** (1) Restructure: split `scheduleAsyncCall` into an accounting part under the lock (`++m_callsExpected`, `++m_remainingToExecute`, state) and a post part after the guard in `onOperationTaskReady` (`:393-455`) and `requestNewAsyncCall` (`:631-646`); the increment happens-before the post, so `onExecute`'s decrement ordering is preserved. (2) TSan suppression file plus a record. Default: (1).
- **Perf.** Same number of lock acquisitions, one shorter critical section.
- **Dependencies.** Do before A-13 (A-13's flag lives in the same functions). Verify: `utf_baselib_async` 4 units, then TSan (`BL_CLANG_ENABLE_RA_TSAN=1 BL_CLANG_ENABLE_RA_FORCE_O1=1`) on `utf_baselib_tasks` and `utf_baselib_async`: the 255 inversion reports must disappear.
- **Size / risk / blast radius / test cost.** ~40 lines / Low-Med (ordering of accounting vs post) / `AsyncExecutorImpl` only / 4 units + TSan.

## A-13 `AsyncOperation::cancel()` while an operation-state task is in progress permanently leaks an executor concurrency slot — High — risk Medium, complexity Medium

- **Decided 2026-09-06: fix, option (1).** Implemented in `async/AsyncExecutorImpl.h`: new `cpp::ScalarTypeIniter< bool > m_cancelPending` in `ExecutorTaskT` (cleared in `resetState()`), set in `requestCancel` on the branch which can only cancel the in-progress operation state task; in `onExecute`, on the call which delivers the callback, the flag causes `m_stopped = true` and one `scheduleAsyncCall( false )`, so the terminating call is posted and - because `m_executeLock` is held for the whole of `onExecute` - can only run after the callback has returned. **Deviation from the review text:** the review says to set `m_stopped` and then schedule; the captured `stopped` value handed to the callback is deliberately taken *before* that assignment, so the result delivered to the caller is byte for byte what it was before the fix (the operation state task was itself cancelled and reports the cancellation through its own exception). Test `AsyncCB_CancelWithOperationTaskInProgressTests` in `utf_baselib_async` (executor with `maxConcurrentTasks = 1`; an operation state whose `createTask()` returns a task latched on a signal; cancel while it is latched, release, then a second operation must execute and call its callback), **shown failing before the fix**: `TestAsyncCB.h(738): fatal error: … critical check ( secondCallbackCalled.wait() ) has failed` (the 10 s bounded wait for the second callback expires because the single concurrency slot is never released). New helper `utest::AsyncTestSignal` in `TestAsyncCommon.h`.

- **Where.** `async/AsyncExecutorImpl.h:548-606` (`ExecutorTaskT::requestCancel`: with `m_operationStateTaskInProgress` it only cancels the inner task, relying on "another cancellation call" after completion, `:569-571`), `:725-727` (`cancel()` → `resetState()`), `:731-753` (`resetState` calls `m_task->requestCancel()` then `m_task.reset()`), `:1155-1193` (`releaseOperation` skips a null `task()`), `:173-335` (`onExecute`).
- **Failure.** After `cancel()` the operation has dropped `m_task`, so the promised second cancellation never reaches the `ExecutorTask`. When the inner task completes: `onOperationTaskReady` → `scheduleAsyncCall( false )` → `onExecute` decrements `m_callsExpected` to 1, invokes the callback and returns with the task still `Running` in `m_workers` (`m_stopped` false). Nothing schedules the terminating call, so one of the `maxExecuting` slots (`padExecutingQueueNothrow`, `ExecutionQueueImpl.h:674-684`) is held until `dispose()`. Production trigger: `TcpBlockTransferServer::cancelTask()` (`TcpBlockTransferServer.h:1504-1508`) calls `m_operation->cancel()` while `AsyncMessageDispatcherWrapper::AsyncOperationStateImplT::createTask()` (`AsyncMessageDispatcherWrapper.h:128-135`) has a task in flight: every client disconnect mid-operation leaks a slot; after `maxConcurrentTasks` (8 × threads) leaks, all new async operations stay pending forever. `TestAsyncCommon.h:116-125` exercises the path but `dispose()` rescues the tasks, so it cannot observe the leak.
- **Design intent.** The comment intends a second terminating call; callback delivery must stay (contract in `AsyncOperation.h`).
- **Options.** (1) `cpp::ScalarTypeIniter<bool> m_cancelPending` in `ExecutorTaskT`, set in `requestCancel` when a state task is in progress; in `onExecute`, when `m_callsExpected` becomes 1 and `m_cancelPending`, set `m_stopped = true` and `scheduleAsyncCall( false )` so the terminating call follows the callback. (2) Keep `m_task` in `resetState()` on the cancel path and let `releaseOperation` issue the second `requestCancel` (changes `resetState` semantics for every caller). Default: (1).
- **Perf.** One bool test per operation completion.
- **Dependencies.** After A-12. Test: after N cancels-with-task-in-progress, `m_workers` holds no `Running` task and a new operation still executes.
- **Size / risk / blast radius / test cost.** ~15 lines / Medium (must not double-terminate) / all `AsyncExecutor` users / 4 units + new case.

## M-3 Broker outbound acceptor registers delivery queues under a self-declared, unauthenticated peer id (delivery hijack) — High — decision

- **Where.** `messaging/TcpBlockTransferServer.h:493-503` (the remote returns its own peer id in the version ack), `messaging/TcpBlockTransferClient.h:635-651` (`m_remotePeerId = m_cmdBuffer.peerId`), `:1095-1160` (`registerQueue` demotes every active queue for that id to `unconfirmedQueues` and makes the new connection the sole active queue), `:1900-1931` (`notifyCallback`), `:1204-1237` (`tryGetQueue` round-robins active queues only).
- **Failure.** On the outbound port (`TcpBlockServerOutgoingT`, no `isAuthenticationRequired` callback; the broker is the blob-protocol client there, so no `Authentication` block is ever exchanged) the only identity is the UUID the remote returns. Any host that can reach the port and knows a victim's peer UUID (present in clear in every `BrokerProtocol` JSON and in debug logs) connects, answers with the victim's id and receives all blocks addressed to the victim, including messages carrying an authorized `securityPrincipal` stamped by `BrokerBackendTask`; repeating the connect keeps the legitimate queues demoted. `BrokerBackendProcessing::peerConnectedNotify` (`:736`) also dissociates the victim's proxy route. The same self-declared identity underlies the full plan's M-15 (`sourcePeerId` only filled when empty, `MessagingUtils.h:213-217`).
- **Design intent.** `:1119-1126` describes a cooperative multi-connection model ("we assume the other connections will confirm themselves quickly"); message-level auth is end-to-end (token → principal) while transport identity is trusted. Prior records decided server-side TLS `verify_none` and fail-closed *client* trust; nothing records the outbound peer-id trust assumption.
- **Options.** (a) Bind outbound registration to the inbound authenticated session: issue a per-peer secret on inbound `Authentication`, echo it in the version-negotiation `DataHeader`'s spare `reserved4`/`unused` field or in a dedicated first block on the outbound leg, refuse `registerQueue` on mismatch; must stay V1/V2 compatible (a peer without the secret behaves as today when authentication is not configured). (b) Record the trusted-network assumption in a decision record; at minimum do not demote existing active queues on a registration coming from a different remote endpoint unless they fail their heartbeat. Default: (b) now, (a) as a scheduled follow-up.
- **Perf.** One map lookup / compare at registration (cold path).
- **Dependencies.** Decision 1; M-4 follows (an authenticated id makes M-4's `sourcePeerId` rule and M-15 fall out).
- **Size / risk / blast radius / test cost.** (a) ~150 lines across server, client, backend state / Medium / broker outbound path / integration test with two connections claiming one id. (b) ~20 lines + record / Low.

## R-4 Unsubscribing (or disposing) an observable from inside its own observer callback deadlocks — Medium — risk Medium, complexity Medium

- **Decided 2026-09-06: option (2) per decision 4 - forbid, assert and document.** Implemented in `reactive/ObservableBase.h`: a `std::shared_ptr< std::atomic< std::thread::id > >` per subscription (created in `subscribe( ... )`, held through a shared pointer so an invoker task which is still executing can always update it), set for the duration of every observer callback by the new `detail::InvokingThreadMarker` - in `ObserverNextInvokerT::run()` and in `notifyObserverComplete` / `notifyObserverError`, which now take the holder as an argument. The new `chkNotCalledFromObserverCallback( ... )` `BL_RT_ASSERT`s with an explanatory message and is called from `unsubscribeInternal( ... )` and from `dispose()` (for every subscription). No deferred-disposal machinery was added. Test: the helper case `Tasks_ReactiveUnsubscribeFromCallbackHelper` (armed only by `-- --unique-id=reentrant-unsubscribe`, so it is a no-op in ordinary runs) unsubscribes from within `onNext`; `Tasks_ReactiveUnsubscribeFromCallbackTests` spawns the test binary itself for that case through `os::createProcess` and requires a non-zero exit. Verified: the child aborts with `RIP: ... An observable can't be unsubscribed or disposed from within an observer callback ...` (exit 134), while the parent case passes.

- **Where.** `reactive/ObservableBase.h:1141-1146` (`unsubscribe` → `unsubscribeInternal( id, wait=true )` under `m_lock`), `:1064-1076`, `:631-654` (`forceFlushNoThrow( wait )` on the subscription's events queue), `:79-86` (`~ObserverDisposerT` → `dispose()` → `unsubscribe`), `:1080-1103` (`dispose()` spins).
- **Failure.** Observer events run as tasks in the per-subscription `eventsQueue`; if `onNext`/`onCompleted`/`onError` drops the `Disposable` returned by `subscribe()`, the flush waits for the executing task, which is the caller, while holding the observable's `TaskBase::m_lock` (stalling its `run()` loop). `ObservableBase::dispose()` from a callback spins forever for the same reason. No `ExecutionQueue` facility detects "called from own task".
- **Design intent.** The disposer is the documented unsubscribe mechanism; events are "always executed serially" (`:210-215`). Keep synchronous unsubscribe for external callers.
- **Options.** (1) Record the invoking thread id in `SubscriptionInfo` from the invoker tasks (`std::atomic< std::thread::id >`, the idiom already in `ExecutionQueueImpl.h`), detect re-entry in `unsubscribe`/`ObserverDisposerT::dispose()` and fall back to `wait=false` with deferred disposal (the `run()` loop already disposes empty queues in `tryFlushObserversEventQueues`). (2) Document as forbidden and `BL_RT_ASSERT` on re-entry (turns a hang into an abort; cheaper, but a contract break for any out-of-tree observer doing it). Default: (1), plus documenting that `dispose()` of the observable must not be called from a callback.
- **Perf.** None on the event path (one atomic store per invocation).
- **Dependencies.** None.
- **Size / risk / blast radius / test cost.** ~30 lines / Medium / all reactive pipelines / 4 units `utf_baselib_tasks` + a case unsubscribing from within `onNext`.

## R-5 `ConversationProcessingBaseImpl::pushMessage()` silently overwrites an unsent pending processing task — Medium — risk Medium, complexity Medium

- **Decided 2026-09-05: fix, option (1), acknowledgments first.** Implemented: `sendMessage()` enqueues into `m_outboundQueue` (`std::deque< MessageInfo >`, bounded by `BLOCK_QUEUE_SIZE`, `TargetPeerQueueFull` beyond it); acknowledgments are inserted ahead of any queued non-acknowledgment message because a baselib peer waiting for an acknowledgment rejects a data message that arrives first; `tryPopProcessingTask()` builds the processing task from the queue front only when no task is pending (a retry created by `retryProcessingTask()` takes precedence) and the popped message becomes the retry message; `onProcessing()` returns early while a send is owed. Scope note: the receiving state machine still rejects an unexpected non-acknowledgment on its next pass (`invalid_argument`), so a duplicate delivery still fails the local conversation; the fix guarantees that the response/acknowledgment already produced reaches the peer instead of being silently dropped (for a duplicate delivery that is the difference between the client obtaining its response and timing out). Test `IO_MessagingMessageProcessingOutboundQueueTests` in `utf_baselib_messaging` (deterministic, no broker: a recording dispatcher, a duplicate request injected between producing and picking up the response, a retried send, and the outbound bound), shown failing before the fix; the four existing `IO_MessagingMessageProcessing*` cases pin the retry and timeout semantics. Downstream: no wire change; peers only receive messages they were waiting for anyway; `tryPopProcessingTask()` lost its `NOEXCEPT`.

- **Where.** `messaging/asyncrpc/ConversationProcessingBaseImpl.h:347-365` (`createProcessingTask` assigns `m_processingTask` unconditionally), `:310-345` (`sendMessage`), `:512-517` (`onProcessing` guards itself with `if( m_processingTask ) return`), `:713-789` (`pushMessage` calls `sendMessage( ack )` with no such guard); `ConversationProcessingTask.h:115-190`, `:205-232` (the task is picked up later in `continuationTask()` → `tryPopProcessingTask()`).
- **Failure.** Between `onProcessing` setting `m_processingTask` and the continuation popping it, an inbound non-ack message (dispatcher thread) replaces `m_processingTask` and `m_retryMessage`; the dropped response/ack is never sent while `m_isAckExpected`/`m_lastSentMessageId` still refer to it, so the conversation dies with the 30 s `TimeoutException` (`:530-538`). Reachable with duplicate/retried deliveries or a peer that sends before receiving the previous ack.
- **Design intent.** One outstanding send at a time, "if there are no current message pop one from the queue".

- **Fix.** After `prctl`, verify `getppid()` equals the pre-fork pid; document the thread constraint or spawn from a long-lived thread (or replace PDEATHSIG with a pipe-based "parent alive" watchdog in the child); `fflush` + tolerate `EPIPE` on the stdin `FILE*` before `reset()` (a non-aborting deleter for that stream); document the `SIGPIPE` requirement. Perf: none.
- **Dependencies.** After O-3 (same function).
- **Size / risk / blast radius / test cost.** ~15-40 lines / Low-Med / `createProcess` users / 2 units + spawn from a short-lived thread and a 1 MB write to `true`'s stdin.

## S-2 Client-controlled token bytes spliced verbatim into the authorization request line and body — Medium — risk Low-Med

- **Where.** `security/AuthorizationServiceRest.h:342-361` (token → `$textToken`, optionally `parsePropertiesList`, into `m_urlPathTemplate->resolve` and `m_requestTemplate->resolve`); `core/StringTemplateResolver.h:279-284` (verbatim substitution); `http/SimpleHttpTask.h:565-570`, `:602-605` (`m_path`/`m_contentIn` written raw). Sources: the gateway's `Cookie` header (`HttpServerBackendMessagingBridge.h:746-790` filters by name only) or any direct broker peer (`BrokerBackendProcessing.h:457-459`, free-form string).
- **Failure.** `"`, `,`, `}` inject into a JSON body template (adding/overriding fields in the request the broker sends under its own TLS identity); ` `, `?`, `#`, `/../` change the request line; CR/LF is injectable from a direct broker peer. Whether this yields privilege depends on the auth service, but the broker forwards structurally corrupted requests it did not intend.
- **Design intent.** "The authentication token is assumed to be a string ... usually passed as HTTP cookies"; `isSecureMode( true )` (`:369`) only redacts the token from exceptions. Keep the template mechanism.
- **Why borderline.** Encoding changes the bytes for tokens that legitimately contain reserved characters (a compatibility change for the URL-path template).
- **Fix.** An optional escaper hook on `resolve()` (`cpp::function< std::string ( const std::string& name, const std::string& value ) >`); percent-encode variables for the URL template, JSON-escape (or reject `"`/`\`/non-printable) for a JSON content type; reject CR/LF/NUL in tokens up front; config flag `escapeTemplateVariables` defaulting to true, release note. Perf: one encode per authorization round trip.
- **Dependencies.** Decision 4.
- **Size / risk / blast radius / test cost.** ~30 lines / Low-Med / broker → auth service hop / 4 units `utf_baselib_security` + template cases with `"`, `?`, space, `\n`.

## W-4 Windows: handle leak, `LSA_UNICODE_STRING`, handle inheritance race, junction print name — Low-Medium — static review only

- **Where / failure.** `core/detail/OSImplWindows.h:1555-1585`: `pi.hThread` closed only on the `assignNewJob` path (kernel handle leak per spawn when already in a job or detached). `:2047-2053`: `LSA_UNICODE_STRING::Buffer` treated as NUL-terminated and non-NULL (UB for system logons). `:1687-1708`, `:898-939`, `:1536-1548`: `_wfopen` handles are inheritable (no `N` mode flag) and `bInheritHandles=TRUE` inherits every inheritable handle, so two concurrent `createProcess` calls cross-inherit pipe ends (a reader sees EOF only when the other child exits; open files held by unrelated children cause delete/rename failures). `:2361-2384`, `:2457`; `:546-551`: `createJunction` strips the last print-name character unconditionally (only correct with the LFN prefix; `back()` on empty is UB); `tryTimedAwaitTermination` compares the wait result rather than `ec` against `STILL_ACTIVE` (dead check).

- **Fix.** Attach `pi.hThread` unconditionally; `std::wstring( Buffer, Length / sizeof( WCHAR ) )` with a NULL check; the `N` mode flag plus an explicit handle list; validate `to.is_absolute()`, compare `ec`.
- **Dependencies.** Decision 10: record into `windows-only-residual-findings-deferral.md` with a `whole-library-windows-residuals-instructions.md` handoff; do not edit blind.
- **Size / risk / blast radius / test cost.** ~35 lines / Low-Med / Windows spawns, registry, junctions / Windows host: argv round-trip scaffold at `TestBaselibDefault.h:1577`, two threads spawning simultaneously with redirect.

- **W-1 `createProcess( vector )` argv quoting — Decided: fix as recommended; the verification method changed.** `OSImplWindows.h` gained `appendQuotedArgument( )`, implementing the documented rule (quote when empty or containing space, tab, newline, vertical tab or `"`; `2n + 1` backslashes before a literal `"`, `2n` before the closing quote, `n` otherwise), and the `std::vector< std::string >` overload now calls it. **The review's suggested oracle - a batch file which echoes its `argv` - cannot work**, for two independent reasons: `cmd.exe` applies its own parsing rather than `CommandLineToArgvW`'s, and its `shift` loop cannot represent an empty argument at all. `::CommandLineToArgvW`, the parser the rule is *defined* by, is used instead and is driven directly against the public static helper, the same way `BaseLib_OSShellEscapeForRunAsUserTests` drives the UNIX twin `transformCommandLineArguments`. `BaseLib_OSCreateProcessArgvQuotingWindowsTests` round-trips ten arguments together and individually, pins the exact emitted text for five, and keeps an end-to-end half through a real child; the `productionArgvQuotingIsFixed` gate is gone. Two corrections to the review text, both recorded in the case: a trailing backslash is **not** by itself a reason to quote, and `::CreateProcessW` does not hand a `.bat` to the command interpreter, so the end-to-end half names `cmd.exe` explicitly.
- **W-2 byte-widened command line — Decided: fix as recommended.** `utf8ToUtf16( commandLine )` into the writable NUL-terminated buffer the call already used. `BaseLib_OSCreateProcessNonAsciiCommandLineWindowsTests` has a child test a non-ASCII path for existence and answer with a pure ASCII word, so the console code page cannot influence the result, plus a negative control.
- **W-3 `tryGetRegistryValue` — Decided: fix as recommended.** `HKEY` initialised to `NULL`, attached to the holder only on `ERROR_SUCCESS`, and `location` derived from the `currentUser` parameter. `BaseLib_OSRegistryHiveDiagnosticsWindowsTests` pins **both** directions of the corrected expression and both places the text is used: `HKEY_LOCAL_MACHINE\SECURITY` (readable by SYSTEM only, so deterministic without administrator rights) for the key open, and a volatile key carrying an over-long `REG_SZ` for the value read. **The UB itself could not be shown failing:** this Windows build does set `*phkResult` to `NULL` on failure, so the pre-fix code read a null rather than a garbage handle; the fix is correct by construction. A **third** defect in the same function is recorded and not fixed - the exception's error code comes from `::GetLastError()`, which the `Reg*` APIs do not set, so the `SECURITY` failure reported `system:6` when the cause was ERROR_ACCESS_DENIED (5).
- **W-4 — Decided: fix (a), (b) and (d); defer (c) to its own plan.** (a) `pi.hThread` is attached to its holder unconditionally; the parent's handle count is **244 before and 244 after** 50 detached spawns. (b) A `lsaString2wstring( )` helper builds the string from `Length / sizeof( WCHAR )` and returns empty for a NULL `Buffer`. (d) `createJunction( )` ensures the substitute name's trailing backslash for **every** spelling of the path, not only inside the long-file-name branch, which is what truncated the print name; a relative target is rejected with `ArgumentException`; and `tryTimedAwaitTermination` compares `ec` rather than the wait result against `STILL_ACTIVE`. **The print-name defect was live on every junction the library creates** - `fs::TmpDir` paths are not prefixed at the point `createJunction` sees them, so the pre-fix print name came back one character short (measured: 100 bytes against 101). **(c), the handle-inheritance race, is deferred — decided, closed and risk-accepted**, recorded in `notes/plans/issues/windows-handle-inheritance-race-deferral.md` with the reasoning, the full implementation design and the triggers that should reopen it. **It is not an open to-do and should not be re-reported as a new finding.** Two reasons: the fix is a conversion of the whole spawn path rather than a localised change - `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` needs `STARTUPINFOEXW`, an allocated attribute list and `EXTENDED_STARTUPINFO_PRESENT` wrapped around logic already intricate with `JOB_OBJECT` / `CREATE_SUSPENDED` / `CREATE_BREAKAWAY_FROM_JOB`, on the most heavily used function in the OS layer, with no consumer asking for it - and **both the handoff text and this review's own W-4 bullet are wrong about the starting point**, claiming the function is "compatible with the existing `STARTUPINFOEXW`" when it builds a plain `STARTUPINFOW` and contains no `STARTUPINFOEX`, `InitializeProcThreadAttributeList` or `EXTENDED_STARTUPINFO_PRESENT` anywhere (verified by grep over `OSImplWindows.h`, 2026-09-08). That error is why the item was sized as a 4-hour job alongside (a), (b) and (d). Exposure is limited because nothing in the repository spawns two redirected children concurrently, which is also why every existing suite is green; the defect is nonetheless real and ships on Windows.
- **N-2 Windows half — Windows verified on 2026-09-08.** `getPhysicalMemorySize()` returns 8 583 315 456 bytes on the recorded host, matching what the OS reports; `getFileDescriptorSoftLimit()` returns 0. `BaseLib_HttpServerDerivedConnectionCapTest` was extended to feed the **real** host values into `getDerivedMaxConnections` and assert that on Windows the descriptor term is skipped, i.e. the cap equals the same arithmetic with that term forced to zero, so the documented fall-back to the RAM term and the 4096 ceiling is covered rather than only the injected-value rows.
- **O-7 Windows half — Windows verified on 2026-09-08.** `RobustNamedMutex`'s `permissions` parameter compiles, is ignored as designed, and `defaultPermissions()` is 0; both spellings of the constructor work. No change. Note that the same constructor's *name* handling was a real defect, fixed as item 9 of the deferral record: it byte-widened the UTF-8 name, so two processes agreeing on a non-ASCII name would not have shared the mutex.

- **`os::fread( )` / `os::fwrite( )` told a transfer error from an end-of-file short transfer by testing `errno` — Decided 2026-09-08 on the Windows host: fix in platform-COMMON code, not behind a per-platform API.** Found while executing the Windows residuals; not part of the W list. The Windows CRT does not set `errno` for a stream-level failure - measured with vc143 / UCRT, `std::fread( )` on a stream opened `"wb"` returns 0 with `errno == 0` and `std::ferror( ) == 1` - so a genuine read error was reported as `"Reading past the end of file"` carrying `EPERM`; `std::fwrite( )` carried the identical defect. **The option of hiding it behind a small API implemented separately in `OSImplWindows.h` and `OSImplUNIX.h` was considered and rejected**, because `std::ferror` is standard C and behaves the same on both platforms (it is set on Windows for exactly the case where `errno` is not), so the two implementations would have been identical copies - the messiness was never platform-variant, the wrong predicate had simply been chosen. Decisive evidence: the library **already carried the correct rule**, in platform-common code, in `stdio_file_device_base::checkStream( )` (`core/detail/OSImplPlatformCommon.h`), whose comment reads "std::ferror returns a flag and not an error code, so the real cause has to come from errno; when it is not available the generic io_error is reported instead" - written before anyone had measured the Windows behaviour it describes. So one `detail::getStdioTransferErrorCode( fileptr, capturedErrno )` was added at the top of the `detail` namespace in that header, and `fread`, `fwrite` and `checkStream( )` all use it: the tree now holds **one** copy of the rule where it held two, and `core/OS.h` follows the house convention instead of its own. **UNIX behaviour is unchanged by construction** - glibc sets both `ferror` and `errno` for this failure, so the same branch is taken and the same `EBADF` attached - and the test became *less* conditional, the `bl::os::onWindows() ? ... : ...` pin in `BaseLib_OSStdioReadWriteErrorTests` being replaced by the single correct expectation plus `UTF_REQUIRE( EPERM != *errNo )`, the assertion which fails against the old discriminator. **Windows-verified only:** `utf_baselib` is green on `vc143` debug and `ccl16` release including `FsUtils_SafeFileStreamWrapperTests` (3010 assertions over the refactored device path); the UNIX half needs a Linux run to be execution-proven rather than inspection-proven. Recorded as item 18 of `notes/plans/issues/windows-only-residual-findings-deferral.md`.
- **`tryGetRegistryValue( )` attached an error code taken from `::GetLastError()` — Decided 2026-09-08: fix.** The `Reg*` family reports through its return value and is not documented to set the last error, so the code on the exception was whatever unrelated call had set it last: the `HKEY_LOCAL_MACHINE\SECURITY` failure reported `system:6` (ERROR_INVALID_HANDLE) where the cause is ERROR_ACCESS_DENIED (5). A third defect in the function W-3 covers, and the same class as W-3's wrong hive text - a misleading diagnostic. `createException( )` gained an overload taking an explicit code and the `::GetLastError()` form now delegates to it, so the `errinfo_file_name` handling is not duplicated; both registry sites pass the status they received. This is the idiom the file already used for the same class of API at its four `*SecurityInfo*` sites. `BaseLib_OSRegistryHiveDiagnosticsWindowsTests` now asserts the code as well as the message. Recorded as item 19 of the same deferral record.
